여러 AWS 계정에 분산되어 있던 CloudTrail, WAF 로그와 자산 정보를 OpenSearch 한 곳으로 수집해 통합 보안 대시보드를 구축한 과정을 정리했습니다. 형식이 서로 다른 로그를 적재 전에 어떻게 표준화했는지, 계정마다 분리된 자산 현황을 어떻게 통합했는지를 중심으로 다룹니다.

왜 이 작업이 필요했나?

저희 AWS 환경은 조직과 용도에 따라 여러 계정으로 분리되어 있습니다. 계정을 구분하면 권한과 비용을 분리하기에는 유리하지만, 보안 관점에서 "지금 전체가 어떤 상태인가"를 파악하려면 계정마다 콘솔을 개별적으로 열어야 했습니다. 보안 데이터가 없었던 것은 아닙니다. CloudTrail, WAF, Config가 생성하는 기록은 이미 존재했는데, 계정과 서비스별로 분산되어 있고 형식도 서로 달라서 한 번에 조회할 수 없었습니다.

그러다 보니 불편한 점이 적지 않았습니다. CloudTrail과 Config 로그가 계정 단위로 분리되어 있어 계정을 아우르는 분석을 수행할 수 없었고, WAF 탐지 결과도 여러 곳에 분산되어 있어 보안 이벤트를 추적하기 어려웠습니다. 월간 보고서는 계정별 현황을 사람이 직접 취합해 작성하느라 시간이 소요됐고, 실시간 알림이 없다 보니 위협이 탐지돼도 조치까지 지연이 발생했습니다.

그래서 목표를 두 가지로 설정했습니다. 보안 로그와 자산 데이터를 한 화면에서 조회하는 것, 그리고 위험한 이벤트는 사람이 확인하기 전에 우선 통보하는 것이었습니다. 저는 DevOps 엔지니어로 이 대시보드 구축을 담당했는데, 로그가 유입되는 경로와 적재 전 변환 로직을 구현하고 각 계정의 자산을 통합하는 수집 구조를 설계한 다음, 그 위에 대시보드와 Slack 알림을 연동하는 일까지 진행했습니다.

어떻게 해결했나

로그와 자산은 다른 경로로 수집하기

수집 대상은 성격이 다른 두 종류였습니다. CloudTrail이나 WAF 로그 같은 보안 이벤트는 시간 순으로 계속 누적되는 스트림이고, EC2, S3, VPC, Security Group, IAM 같은 자산 현황은 특정 시점의 상태입니다. 그래서 수집 경로도 둘로 분리했는데, 보안 로그는 CloudWatch Logs에서 Firehose와 Transform Lambda를 거쳐 OpenSearch로 전달되는 스트리밍 경로로, 자산 정보는 중앙에서 각 계정에 AssumeRole로 접근해 조회하는 방식으로 수집합니다. 두 데이터는 같은 OpenSearch에 적재되어 하나의 대시보드에서 함께 조회하게 되고, Config나 Security Hub 같은 다른 보안 이벤트도 같은 저장소로 통합했습니다.

표준화는 적재 전에 한 곳에서

CloudTrail과 WAF 로그는 스키마가 다르고, CloudTrail은 같은 서비스 안에서도 API마다 필드 구조가 달라집니다. 이 상태로 OpenSearch에 적재하면 같은 필드 이름에 다른 타입의 값이 유입되어 매핑 충돌이 발생하기 쉽습니다. 그래서 인코딩, 문서 형식, 시간대, 필드 구조를 Firehose의 Transform Lambda에서 모두 통일한 다음 적재하도록 했습니다.

이렇게 하면 인덱스와 대시보드를 "필드가 이미 정리되어 유입된다"는 전제로 설계할 수 있어서 OpenSearch 측 구성이 단순화됩니다. 대신 변환 규칙이 Lambda 한 곳에 집중되기 때문에 새 로그 유형을 추가할 때마다 이 코드를 함께 수정해야 하고, 모든 계정의 로그가 이 경로 하나를 경유한다는 점도 함께 감수해야 했습니다.

대시보드는 조회하는 곳, 알림은 우선 통보하는 곳

대시보드는 누군가 열어 확인해야 의미가 있습니다. 탐지 후 조치까지 발생하던 지연을 줄이려면 고위험 이벤트는 사람이 확인하기 전에 우선 전달돼야 했기 때문에, 고위험 이벤트는 Slack으로 즉시 통보하고 대시보드는 추세와 맥락을 확인하는 곳으로 역할을 분리했습니다.

대시보드는 "무슨 일이 있었나"와 "어디서 많이 일어나나"를 함께 확인할 수 있게 구성했습니다. 이벤트 영역에는 CloudTrail 이벤트, Root 계정 로그인 시도, 리소스 변경, WAF 탐지 현황 패널을 배치했고, 집계 영역에서는 Region별 이벤트 수와 자주 등장하는 IP와 Action, 자산 유형별 비율을 확인할 수 있게 했습니다.

까다로웠던 부분

형식이 다른 로그를 동일한 문서 규칙으로

CloudWatch Logs를 거쳐 Firehose로 유입되는 데이터는 여러 로그 이벤트가 한 묶음으로 전달됩니다. Transform Lambda는 이 묶음을 OpenSearch가 수용할 수 있는 문서로 변환하는 단계인데, 먼저 이벤트를 한 줄에 하나씩 UTF-8 NDJSON 문서로 분리해 _bulk 색인 형식에 맞췄습니다. 로그마다 상이한 시간 표기는 KST로 통일해서 CloudTrail 이벤트와 WAF 탐지를 같은 시간 축에서 비교할 수 있게 했습니다. API 호출 종류에 따라 달라지는 중첩 구조는 평탄화(Flatten)해 매핑 충돌을 방지했고, 색인은 대량 데이터를 일괄 전송하는 방식으로 처리해 로그가 집중될 때도 수집이 안정적으로 유지되도록 했습니다.

계정마다 키를 발급하지 않고 자산 수집하기

자산 수집은 중앙에서 각 계정의 Role을 AssumeRole로 수임해 정보를 조회하는 방식입니다. 계정마다 접근 키를 별도로 발급해 관리하지 않아도 된다는 점이 이 방식의 장점이었습니다. 수집 대상은 EC2, S3, VPC, Security Group, IAM 같은 주요 자산이고, 수집한 자산은 자산 요약 인덱스 하나로 통합한 뒤 계정명과 자산 유형을 기준으로 카운트를 집계해 대시보드에 반영했는데, 매달 계정별 콘솔을 열어 현황을 파악하던 일을 대시보드 한 장으로 대체하려는 의도였습니다. Tag를 기준으로 자산을 분류하는 작업도 자동화했습니다.

결과

이제 여러 계정, 여러 서비스의 보안 로그를 한 곳에서 준실시간으로 조회할 수 있고, 자산 현황과 보안 이벤트, 위협 탐지 결과를 한 화면에서 확인합니다. 고위험 이벤트는 누군가 대시보드를 열기 전에 Slack으로 우선 전달됩니다. 계정별로 사람이 취합하던 현황이 한 저장소에 통합됐기 때문에 월간 보안 운영 보고서를 자동화할 수 있는 기반도 마련됐습니다. 적재 전 변환 단계가 별도로 분리되어 있어서, 이벤트 위험도를 점수화하는 것 같은 후속 자동화를 추가할 여지도 있습니다.

돌아보며

AWS는 이미 필요한 기록을 생성하고 있었고, 가시성을 저해하던 것은 수집보다 형식이 상이한 로그를 동일한 규칙으로 표준화하는 일이었습니다. 이 단계를 적재 전 한 곳에 배치한 덕분에 시각화와 알림 측은 단순하게 유지할 수 있었습니다.
